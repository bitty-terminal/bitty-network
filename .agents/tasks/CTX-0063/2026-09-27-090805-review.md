# Baseline and permanent proxy rejection tests for #25 (Criterion 3)

This PR hardens the regression coverage for the fail-closed proxy rejection contract that issue #25 (Criterion 3) requires: an explicit credentialed proxy URL, an unparseable ambient `HTTPS_PROXY`/`https_proxy`, and a credentialed WebSocket proxy must all be rejected before any socket is touched and before the URL is retained anywhere observable. It adds one `HttpNetworkService::with_proxy` unit test with a live loopback listener to prove zero dial attempts, strengthens the existing WebSocket rejection test to also assert the destination is never dialed (previously only the proxy leg was checked), and adds a child-process test proving an unparseable `HTTPS_PROXY` poisons construction, fails every request closed, leaks nothing into `Debug`/`Display`, and never falls back to direct egress. No production logic changed — this is regression-test-only, confirmed by diff scope.

Watch for: the PR was merged (`mergedAt` 2026-09-27T09:02:42Z) by its own author with zero recorded GitHub reviews (**confirmed** — `gh pr view --json reviews` returns `[]`, `mergedBy` equals `author`), which is a governance violation independent of code correctness; a GitHub review attempt from this reviewer identity fails outright because the CLI is authenticated as the same account as the PR author (**confirmed** by the GraphQL rejection).

## High-level view

The new tests are real regression tests, not tautological assertions: mutation testing (temporarily removing the credential/userinfo check in `proxy_url_has_credentials` and the fail-closed check in `ensure_proxy_usable`, then reverting) makes both new tests fail exactly as expected, and no other test in the suite masks the removal. The credential-leak assertions hold under mutation too — the panic message from the mutated run itself surfaces the service's `Debug` output and confirms it carries `proxy_configured`/`proxy_rejected` booleans only, never the URL or the `fixture-user`/`fixture-pass` strings.

The WebSocket test strengthening closes a real prior gap: the old version only proved the proxy listener wasn't dialed, leaving the destination leg unverified after `tunnel_via_proxy`'s early return. The new version binds a second loopback listener for the destination and asserts it too is never dialed, which is the correct fix and not scope creep — the fail-closed claim in the PR title was previously half-proven.

The child-process test for the unparseable-ambient-proxy path is appropriately isolated: it needs `Command::new(current_exe())` re-invocation because environment-variable proxy configuration is read once at service construction and the assertions differ by whether the `proxy` feature is compiled in, which cargo's single-process test harness cannot vary per-test. The test correctly asserts both feature configurations (`AMBIENT_ENV_APPLIED` true and false) rather than just one, avoiding a common trap where a feature-gated test only proves itself under one build.

### Mutation-tested regression coverage, not tautological

`explicit_credentialed_proxy_is_rejected_before_retaining_or_dialing` (new, `http.rs`) binds a real loopback `TcpListener`, passes its address inside a credentialed proxy URL to `HttpNetworkService::with_proxy`, and asserts both `NetworkError::Offline` and that `listener.accept()` returns `WouldBlock` (i.e., no connection was ever accepted). Reverting `proxy_url_has_credentials` to always return `false` made this test fail with a panic showing the service's `Debug` representation — which is also useful evidence that the redacting `Debug` impl (`proxy_configured`, `proxy_rejected` booleans only) does not leak the credentialed URL even in the failure/panic path.

`unparseable_https_proxy_environment_fails_closed_without_direct_fallback` (new, `tests/http.rs`) re-execs the test binary as a child process with `HTTPS_PROXY`/`https_proxy` set to `"://malformed-proxy-url"`, and checks under both proxy-feature configurations that: the malformed URL never appears in captured stdout/stderr, the request fails with `NetworkError::Offline` (proxy feature on) or reaches the origin directly (proxy feature off — the correct behavior since the environment isn't read at all in that build), the `Debug` output reports `proxy_rejected: true`/`proxy_configured: false`, and a second request on the same poisoned service also fails closed rather than only failing once. Reverting `ensure_proxy_usable` to unconditionally return `Ok(())` made this test fail in both the parent-process assertion (`unparseable proxy child process failed`) and the child-process assertion (`unparseable ambient proxy must fail closed`), confirming the test is watching the actual fail-closed gate rather than a vacuous condition.

### WebSocket destination-dial gap closed

The pre-existing `authenticated_proxy_is_rejected_before_dial` only bound one loopback listener (the proxy) and pointed the destination at a `closed_port()` helper, so it never actually proved the destination side of `tunnel_via_proxy` was unreached — a bug that made the destination dial happen anyway (e.g., a missing early return) would have produced the same `NetworkError::Offline` from a connection-refused on the closed port, indistinguishable from the intended pre-dial rejection. The PR replaces `closed_port()` with a second live loopback listener and adds the same non-blocking-accept assertion against it, which is the right fix for a fail-closed claim that spans two dial legs (proxy and destination).
